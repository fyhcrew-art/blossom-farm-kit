# Network: the domain, the tunnel, and what travels where

## 1. Before the installer: a domain at Cloudflare

The tunnel needs a domain whose DNS is managed by Cloudflare.

1. Create a free account at <https://dash.cloudflare.com>.
2. Add your domain ("Add a domain"), choose the Free plan.
3. Cloudflare shows two name servers. Enter them at the company where you
   bought the domain (its "name servers" setting), replacing the old ones.
4. Wait until the Cloudflare dashboard shows the domain as **Active**. This
   takes minutes to a day.

If the domain already carries a website or e-mail, check that Cloudflare
imported its existing DNS records before you switch the name servers. A
separate, cheap domain used only for the farm avoids any risk to an existing
site.

Choose three host names that are **direct sub-domains** of the domain:

```
farm-hub.yourdomain.com
farm-provider.yourdomain.com
farm-restart.yourdomain.com
```

Not `hub.farm.yourdomain.com`: the certificate Cloudflare issues for free
covers `yourdomain.com` and `*.yourdomain.com`, one level only.

## 2. What the installer does with Cloudflare

These are the documented Cloudflare Tunnel steps for a locally managed
tunnel
([Cloudflare documentation](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/create-local-tunnel/));
the installer runs them for you:

| Command | Effect |
|---|---|
| `cloudflared tunnel login` | Opens a browser; you sign in and authorise one domain. Writes an account certificate, `cert.pem`. |
| `cloudflared tunnel create blossom-farm` | Creates the tunnel and a credentials file for it. |
| `cloudflared tunnel route dns <tunnel> <host name>` (three times) | Creates a CNAME record for each host name, pointing at `<tunnel id>.cfargotunnel.com`. |
| writes `C:\farm\config\cloudflared\config.yml` | Says which host name goes to which local port. |
| `cloudflared tunnel --config … ingress validate` | Checks that file. |
| service `Cloudflared`: `cloudflared tunnel --no-autoupdate --config … run` | Runs the tunnel, from now on with every start of the PC. |

The two files Cloudflare gives you are different in power
([Cloudflare: tunnel permissions](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/tunnel-permissions/)):

* `tunnel-credentials.json` can only *run this one tunnel*. The service needs
  it.
* `cert.pem` can create, route and delete *all tunnels of the account*. It is
  only needed while setting up. The installer moves it out of your user
  profile into `C:\farm\config\cloudflared\` (Administrators only) so that
  re-runs and `uninstall.ps1 -RemoveData` can use it. If you prefer, delete it
  after installation; you will be asked to sign in again the next time a DNS
  record has to be created.

The configuration file looks like this (yours has your names):

```yaml
tunnel: 00000000-0000-0000-0000-000000000000
credentials-file: 'C:\farm\config\cloudflared\tunnel-credentials.json'

ingress:
  - hostname: farm-hub.yourdomain.com
    path: '(?i)appium'
    service: http_status:403
  - hostname: farm-hub.yourdomain.com
    path: '^/provider-update'
    service: http_status:403
  - hostname: farm-hub.yourdomain.com
    service: http://127.0.0.1:10000
  - hostname: farm-provider.yourdomain.com
    service: http://127.0.0.1:10002
  - hostname: farm-restart.yourdomain.com
    service: http://127.0.0.1:19999
  - service: http_status:404
```

* The provider's host name leads to port **10002**, the provider gate, never
  to 10001, the provider itself. `docs/security.md` says why.
* The two `path` rules refuse, before they reach the hub, requests that
  Blossom never makes and that GADS 6.0.0 would accept without a login
  (`docs/security.md`, "What GADS itself does not protect").
* The last rule is the catch-all that Cloudflare requires.

Do not edit this file by hand: `install.ps1` rewrites it. If you need a
change, open an issue.

## 3. What the PC needs from your network

* **Outgoing** connections only. No port forwarding, no fixed IP address, no
  DynDNS.
* cloudflared connects to Cloudflare on **port 7844** (TCP and UDP). A
  firewall that only allows web traffic (ports 80/443) blocks it; Cloudflare's
  documentation lists this as the thing to check behind a restrictive
  firewall.
* **Outgoing UDP** in general, for the live video (next section).
* A **wired** connection. The farm's upload speed carries every live screen
  somebody is watching.
* Nothing needs to reach the PC from your local network. All farm programs
  listen on `127.0.0.1`; `scripts\status.ps1` verifies it.

## 4. What travels where

| From | To | What |
|---|---|---|
| Blossom's servers | hub host name | sign-in, the phone list, settings |
| Blossom's servers | provider host name (through the gate) | taps and screenshots made by the AI assistant, downloads to a phone, auto-lock |
| Blossom's servers | restart host name | status and the restart buttons of the Services panel |
| A team member's browser | hub host name | taps, swipes, typing from the Control page |
| A team member's browser | provider host name (through the gate) | a WebSocket that carries the WebRTC handshake only |
| A team member's browser | **the farm PC directly** | the live video itself (WebRTC, UDP, encrypted, peer to peer) |

The live video does **not** go through the tunnel and not through Blossom.
After the short handshake the browser and the PC send to each other directly.
To find a path through both routers they use a STUN server; GADS 6.0.0 ships
with Google's public one (`stun.l.google.com:19302`) as its default, and a
TURN relay can be configured in the hub page (Admin, TURN settings) for
networks where no direct path forms. Whether Blossom adds a relay of its own
depends on the deployment; its Control page shows *Direct* or *Relay* per
phone.

Consequence worth knowing: during a live video session, the watching browser
and the farm PC learn each other's public IP address. That is how WebRTC
works.

## 5. Cloudflare settings to leave alone, and one to consider

* **WebSockets** (dashboard → your domain → Network): must stay on. It is on
  by default.
* **Do not add** a Cloudflare Access application, an "Under Attack" mode, a
  managed challenge or a bot-fight rule for the three host names. Blossom's
  servers and the Control page call the farm with plain API requests and
  cannot answer a login page or a challenge; "Test connection" then fails.
  (`docs/security.md` explains what was checked in the product.)
* **Consider** a rate-limiting rule for `POST /authenticate` on the hub host
  name (dashboard → Security → WAF → Rate limiting rules; the free plan
  includes one rule). GADS itself does not slow down password guessing.
  A limit such as 10 requests per minute per IP address does not get in
  Blossom's way: it signs in rarely and reuses the session.
* Limits of Cloudflare's free plan that matter here: a request must be
  answered within 100 seconds, and an upload may be 100 MB at most. Neither is
  reached by what Blossom does. For large uploads to the hub (an app file),
  use the hub's page on the PC itself, `http://127.0.0.1:10000`.

## 6. Another tunnel service?

Blossom only needs three fixed https host names with valid certificates that
reach the three local ports. Any service that provides that works with the
product. This kit automates Cloudflare Tunnel only; with another service you
would install the six services with `install.ps1`, stop at the tunnel step,
and wire the host names yourself: hub → `127.0.0.1:10000`, provider →
`127.0.0.1:10002` (the gate, **not** 10001), restart → `127.0.0.1:19999`. Free
"quick" tunnels with a random name that changes on every start are of no use.
