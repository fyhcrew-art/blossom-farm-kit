# Network: the domain, the tunnel, and what travels where

## 1. Before the installer: a domain at Cloudflare

The tunnel needs a domain whose DNS is managed by Cloudflare.

1. Create a free account at <https://dash.cloudflare.com>.
2. Add your domain ("Add a domain"), choose the Free plan.
3. Cloudflare shows two name servers. Enter them at the company where you
   bought the domain (its "name servers" setting), replacing the old ones.
4. Wait until the Cloudflare dashboard shows the domain as **Active**. This
   takes minutes to a day.

If the domain already carries a website or e-mail, check that Cloudflare
imported its existing DNS records before you switch the name servers. A
separate, cheap domain used only for the farm avoids any risk to an existing
site.

Choose three host names that are **direct sub-domains** of the domain:

```
farm-hub.yourdomain.com
farm-provider.yourdomain.com
farm-restart.yourdomain.com
```

Not `hub.farm.yourdomain.com`: the certificate Cloudflare issues for free
covers `yourdomain.com` and `*.yourdomain.com`, one level only.

## 2. What the installer does with Cloudflare

These are the documented Cloudflare Tunnel steps for a locally managed
tunnel
([Cloudflare documentation](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/create-local-tunnel/));
the installer runs them for you:

| Command | Effect |
|---|---|
| `cloudflared tunnel login` | Opens a browser; you sign in and authorise one domain. Writes an account certificate, `cert.pem`. |
| `cloudflared tunnel create blossom-farm` | Creates the tunnel and a credentials file for it. |
| `cloudflared tunnel route dns <tunnel> <host name>` (three times) | Creates a CNAME record for each host name, pointing at `<tunnel id>.cfargotunnel.com`. |
| writes `config.yml` in the farm's `config\cloudflared` folder (`C:\farm\…` on Windows, `/opt/farm/…` on macOS) | Says which host name goes to which local port. |
| `cloudflared tunnel --config … ingress validate` | Checks that file. |
| the tunnel service (`Cloudflared` on Windows, `blossom-farm.cloudflared` on macOS): `cloudflared tunnel --no-autoupdate --config … run` | Runs the tunnel, from now on with every start of the computer. |

The two files Cloudflare gives you are different in power
([Cloudflare: tunnel permissions](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/tunnel-permissions/)):

* `tunnel-credentials.json` can only *run this one tunnel*. The service needs
  it.
* `cert.pem` can create, route and delete *all tunnels of the account*. It is
  only needed while setting up. The installer keeps it in the farm's
  `config\cloudflared` folder, for Administrators only on Windows and for
  root only on macOS, so that re-runs and the uninstall script with
  `-RemoveData` / `--remove-data` can use it. If you prefer, delete it after
  installation; you will be asked to sign in again the next time a DNS record
  has to be created.

On macOS the tunnel itself does not run as root: it runs as the farm's
service account, which may read `tunnel-credentials.json` and `config.yml`
and nothing of `cert.pem`.

The configuration file looks like this (yours has your names):

```yaml
tunnel: 00000000-0000-0000-0000-000000000000
credentials-file: 'C:\farm\config\cloudflared\tunnel-credentials.json'   # macOS: '/opt/farm/config/cloudflared/tunnel-credentials.json'

ingress:
  - hostname: farm-hub.yourdomain.com
    path: '(?i)appium'
    service: http_status:403
  - hostname: farm-hub.yourdomain.com
    path: '^/provider-update'
    service: http_status:403
  - hostname: farm-hub.yourdomain.com
    path: '^/admin/provider/[^/]+/info'
    service: http_status:403
  - hostname: farm-hub.yourdomain.com
    service: http://127.0.0.1:10000
  - hostname: farm-provider.yourdomain.com
    service: http://127.0.0.1:10002
  - hostname: farm-restart.yourdomain.com
    service: http://127.0.0.1:19999
  - service: http_status:404
```

* The provider's host name leads to port **10002**, the provider gate, never
  to 10001, the provider itself. `docs/security.md` says why.
* The three `path` rules refuse, before they reach the hub, requests that
  Blossom never makes and that GADS 6.0.0 would accept without a login
  (`docs/security.md`, "What GADS itself does not protect"). The self-test
  checks from outside that they answer 403.
* The last rule is the catch-all that Cloudflare requires.

Do not edit this file by hand: the installer rewrites it. If you need a
change, open an issue.

## 3. What the computer needs from your network

* **Outgoing** connections only. No port forwarding, no fixed IP address, no
  DynDNS.
* cloudflared connects to Cloudflare on **port 7844** (TCP and UDP). A
  firewall that only allows web traffic (ports 80/443) blocks it; Cloudflare's
  documentation lists this as the thing to check behind a restrictive
  firewall.
* **Outgoing UDP** in general, for the live video (next section).
* **Outgoing https (port 443) to your Blossom**, on a paired computer: the
  installer and the `rotate-secrets`, `update`, `status` and `uninstall`
  scripts call Blossom's pairing API there (`docs/security.md`, section 9).
  The connection must reach Blossom untouched: a proxy or security product
  that opens encrypted connections makes the certificate check fail, and the
  scripts then send nothing. During the setup the computer also downloads
  from `github.com` and from the publishers named in `versions.json`.
* A **wired** connection. The farm's upload speed carries every live screen
  somebody is watching.
* Nothing needs to reach the computer from your local network. The hub, the
  provider, the gate, the restart service and MongoDB listen on `127.0.0.1`
  only. The ports the provider opens for each connected iPhone are different:
  GADS opens them on all addresses of the computer, and the kit refuses
  connections to them from other computers: with Windows Firewall rules on
  Windows, with a rule in the packet filter (pf) on macOS
  (`docs/security.md`, section 1). The status script checks both. Keep that
  firewall switched on.
* On a Mac that rule drops every new TCP connection from the network to the
  Mac's range of temporary ports (49152 to 65535). Nothing the farm needs
  arrives there, and neither do Screen Sharing (5900), Remote Login (22) or
  file sharing (445). What it does stop is anything else on the Mac that
  waits for connections on a port of that range; features of macOS that link
  your own Apple devices to the Mac (Handoff, Universal Control) can be
  among them.

## 4. What travels where

| From | To | What |
|---|---|---|
| Blossom's servers | hub host name | sign-in, the phone list, settings |
| Blossom's servers | provider host name (through the gate) | taps and screenshots made by the AI assistant, downloads to a phone, auto-lock |
| Blossom's servers | restart host name | status and the restart buttons of the Services panel |
| A team member's browser | hub host name | taps, swipes, typing from the Control page |
| A team member's browser | provider host name (through the gate) | a WebSocket that carries the WebRTC handshake only |
| A team member's browser | **the farm computer directly** | the live video itself (WebRTC, UDP, encrypted, peer to peer) |
| The farm computer (installer, scripts) | your Blossom, https | on a paired computer: the pairing code once; the farm's addresses, hub login and restart secret when they are made or changed; the versions it runs; questions about the state of its pairing |

The live video does **not** go through the tunnel and not through Blossom.
After the short handshake the browser and the computer send to each other directly.
To find a path through both routers they use a STUN server; GADS 6.0.0 ships
with Google's public one (`stun.l.google.com:19302`) as its default, and a
TURN relay can be configured in the hub page (Admin, TURN settings) for
networks where no direct path forms. Whether Blossom adds a relay of its own
depends on the deployment; its Control page shows *Direct* or *Relay* per
phone.

Consequence worth knowing: during a live video session, the watching browser
and the farm computer learn each other's public IP address. That is how WebRTC
works.

## 5. Cloudflare settings to leave alone, and one to consider

* **WebSockets** (dashboard → your domain → Network): must stay on. It is on
  by default.
* **Do not add** a Cloudflare Access application, an "Under Attack" mode, a
  managed challenge or a bot-fight rule for the three host names. Blossom's
  servers and the Control page call the farm with plain API requests and
  cannot answer a login page or a challenge; "Test connection" then fails.
  (`docs/security.md` explains what was checked in the product.)
* **Browser Integrity Check** (dashboard → your domain → Security → Settings)
  is **on by default** on every Cloudflare domain. Cloudflare's documentation
  says it challenges requests that come without a User-Agent header, and at
  the time of writing Blossom's servers send none on their calls to a farm.
  We have not seen it block a farm, and we cannot promise that it never
  does. If "Test connection" in Blossom fails at *Secure connection* or *Hub
  sign-in* with an error page (HTML, or HTTP 403) although the computer is fine,
  switch Browser Integrity Check off, or add a configuration rule that
  switches it off for the three farm host names only. The kit's self-test
  sends its requests the way Blossom does (without a User-Agent) and names
  this setting when Cloudflare answers with its own block page.
* **A rate-limiting rule on the sign-in is optional, and easy to get wrong.**
  GADS does not slow down password guessing, so a rule for `POST
  /authenticate` on the hub host name looks attractive (dashboard → Security
  → WAF → Rate limiting rules). Know two things before you add one:
  * Blossom signs in to the hub **often**, not rarely: at the time of
    writing, every refresh of the phone list is a new sign-in. One open Phone
    Farm page is about one sign-in every 10 seconds; each further page, team
    member and opened Control screen adds its own. They all come from
    Blossom's servers, that is from few IP addresses.
  * On Cloudflare's **Free** plan a rate-limiting rule counts over **10
    seconds** and blocks for 10 seconds; a per-minute rule needs a paid plan.

  A rule that fires on normal use makes the phone list and Control fail on
  and off ("server unreachable", error 429). If you add one, make it
  generous, for example more than **30** requests in 10 seconds from one IP
  address, and raise it if Blossom shows such errors. A rule like that stops
  a flood, not a patient guesser. What actually protects the sign-in is that
  the passwords are long and random: the kit generates 256-bit ones for
  `blossom`, and the one you choose for `admin` must be long (the installer
  enforces 14 characters; more is better).
* Limits of Cloudflare's free plan that matter here: a request must be
  answered within 100 seconds, and an upload may be 100 MB at most. Neither is
  reached by what Blossom does. For large uploads to the hub (an app file),
  use the hub's page on the computer itself, `http://127.0.0.1:10000`.

## 6. Another tunnel service?

Blossom itself only needs three fixed https host names with valid
certificates that reach the three local ports: hub → `127.0.0.1:10000`,
provider → `127.0.0.1:10002` (the gate, **not** 10001), restart →
`127.0.0.1:19999`. Any service that provides that works with the product.

**This kit does not support another tunnel service.** The installer (on
Windows and on macOS) cannot finish without Cloudflare: it has no switch to
leave the tunnel out, and the restart secret and the provider, gate,
keep-available and restart services are created only after the tunnel step.
Stopping the installer there leaves a computer with a hub and nothing else.
With another service you would have to create those services and the three
path refusals of section 2 yourself, from the files in `services/` and the
settings in the installer; the kit does not describe that. Free "quick" tunnels with a random name that
changes on every start are of no use in any case.
